# Jarvis: voice and agent integration review

Research and implementation review, 12 September 2026. Target: the existing Electron/native/MLX application on Victor's M1 Pro with 16 GB unified memory. This continues the supplied eight-milestone plan. It does not replace the orb design or the task ledger.

## Recommendation

Keep the current local stack as the default: native echo-cancelled capture and playback, openWakeWord, streaming Silero, Smart Turn, small Whisper, Qwen 3.5, and Kokoro. Preserve LFM Audio as a separately selectable local audio model. Use OpenAI Realtime as an explicit paid voice route, feeding the same task engine and memory boundaries. The most consequential defects in this checkout were integration defects. A larger model alone would not repair microphone/playback races, premature end-of-stream handling, missing tool dispatch, or an unavailable credential form.

For this hardware, the next model replacement should earn its place through an end-to-end latency and quality comparison. A model card claiming subsecond response on an H100 or M4 Max is not evidence of that performance on an M1 Pro. Testing every model on Hugging Face is neither a bounded nor a useful acceptance criterion. This investigation tests every installed catalog model, inspects the two remaining catalog profiles, and compares the most relevant maintained alternatives across the entire voice and agent path.

## What the user should experience

“Hey Jarvis” opens a turn without a click. A short natural pause finishes a completed thought; an unfinished phrase gets more time. A spoken answer starts while generation continues, stays brief, and can be interrupted. Follow-up listening resumes after the final audio piece, then returns to wake-word standby after inactivity. Asking for work creates a durable task, whose proposed effects and observed results are visible in the existing panels. Corrections influence future replies through scoped memory.

That experience involves several independent systems. Wake-word recognition asks whether the activation phrase occurred. VAD asks whether speech is present. A turn detector asks whether the thought has ended. Echo cancellation removes the assistant's playback from microphone input. Cancellation invalidates queued text and audio. The agent executes tools and checks outcomes. Memory makes useful information available on later turns. None substitutes for the others.

## Confirmed integration gaps and changes

| Gap found in the checkout | Change | Verification boundary |
| --- | --- | --- |
| Opening a microphone changed the generation used to accept playback chunks | Independent capture and playback generations; cleanup checks the capture it belongs to | Real native lifecycle harness |
| An empty playback queue was treated as a finished answer while the model still generated | Explicit stream begin/end; starvation is allowed; final completion emitted once | Real native playback with delayed chunks |
| Wake scoring competed with language generation and used temporary audio snapshots | Wake detection runs on the streaming listener thread with a bounded in-memory history | Installed model fixtures plus streamed listener checks |
| Speech stopping did not reliably stop pending generation | Conversation abort and output cancellation share the interruption path; stale chunks are rejected | Native lifecycle and protocol tests; human acoustic trials remain |
| Reply instructions could drift into several sentences | Sentence and token bounds on local text generation; existing duration bounds retained for LFM | Real model qualification and app conversation check |
| OpenAI appeared as a connection, but had no working voice transport | Service-owned WebSocket connection, 24 kHz native PCM, semantic VAD, cancellation/truncation, transcripts, task tools and bounded sessions | Protocol tests and live hosted speech with synthesized input |
| OpenAI credential entry could not be expanded | Correct connection-form routing; truthful voice/privacy copy | Actual Settings interaction |
| Conversation dispatched only a few native task phrases | Explicit action routing plus a model sentinel forwards original user instructions to the existing task engine | Intent tests and task-ledger integration |
| MCP discovered tools but did not execute them | Schema validation, exact-call approval, identity/schema revalidation, effect receipts and cancellation | Controlled MCP contract test |
| No general local execution loop or installable skill packages | Bounded local planner; scoped reads; reviewed sandboxed commands in isolated worktrees; Agent Skills packages | Encrypted ledger tests, real Qwen skill installation and isolated command execution |
| “Self improvement” lacked an outcome-linked path for agent work | Successful work can propose a scoped procedural lesson referencing its task; review is required before recall | Scoped memory test |
| Other duplex model IDs inherited installability from a shared role | Exact model-adapter capability list | Worker capability reporting; research profiles remain disabled |

The local agent reuses the existing revision, approval, uncertainty, receipt and recovery machinery. Commands receive a private HOME and an isolated worktree. Network access is explicit and is rechecked before dispatch. Modified worktrees require configured project checks on the exact file fingerprint; review evidence includes new files as well as tracked diffs. No commit or publication is implied by a successful task. System-wide installation is outside that sandbox; it is not honestly described as an ability to install “anything.”

The original native file, Calendar, Reminders and Accessibility paths remain separate where their semantics differ. Agent Skills are reviewed instruction packages, not unrestricted executable plugins. MCP servers supply connected tools. Arbitrary OpenClaw, Claude or Codex plugin bundles are not automatically interchangeable with Jarvis: manifests, hooks, credentials and runtime contracts need explicit adapters.

The streamed turn-detector check used real-time-paced audio frames. A finished question scored 0.957 in 111 ms; an unfinished thought scored 0.031 in 34 ms; silence caused no speech transitions. Those numbers exclude the deliberate pause before asking the turn detector. They are not a claim of 111 ms end-to-end spoken response. See [turn-detection.json](./turn-detection.json).

The native stop harness completed 100 trials with p95 13.79 ms and maximum 15.57 ms at the NDJSON-to-playback-stop-acknowledgment boundary. Acoustic leakage testing found 77.5% speech frames on the raw microphone while the speaker played the fixture, versus zero on the processed route. The out-of-engine playback comparison also measured zero on this macOS route, so that comparison does not establish that only engine-routed playback is cancelled by the operating system. The raw-microphone control establishes that the speaker was audible. See [native-audio.json](./native-audio.json), [voice-lifecycle.json](./voice-lifecycle.json), and [barge-in.json](./barge-in.json).

The wake listener also ran while Qwen generated a long answer. It detected the streamed name once at 1.78 seconds from the start of a fixture that included leading silence; unrelated speech and silence did not wake it. Generation was still active at detection. This tests scheduling with synthesized speech, not human wake accuracy. See [wake-stream.json](./wake-stream.json).

Real Qwen agent trials read a temporary project in 7.28 seconds, installed the reviewed test skill in 16.39 seconds, and ran an approved `/usr/bin/true` in an isolated worktree in 5.87 seconds. The harness used the actual model and encrypted ledger, approving only those exact fixture effects. Earlier trials caught a rejected root-directory path, incorrect skill paths, and premature completion after merely reading instructions. The executor now allows bounded correction of read errors and requires matching effect receipts for explicit work requests. These three tasks do not establish broad coding competence. See [local-agent.json](./local-agent.json).

The Electron app preserved the 72-point orb and passed automated WCAG checks across all eight Settings sections after fixing a meter role and a footer label's contrast. Two short replies reached playback state in 2.79 and 4.22 seconds in the expanded development run; earlier runs were 2.00 and 2.33 seconds. These are typed-request app timings with differing load and history, not acoustic first-sound measurements. See [app-integration.json](./app-integration.json).

A first signed-installation trial was substantially slower: 13.82 and 7.30 seconds. The first request overlapped a 23.4-second startup warmup. Startup warming is now split into cancellable role requests, foreground input prevents further background roles from queuing, and empty recall avoids an unnecessary embedding request. The worker logs queue delay, first-token time, synthesis time and prompt size for real app conversations. The subsequent signed local run measured 8.88 seconds on its first typed request and 5.08 seconds on the next. Queue delay was 489 ms then 1 ms; model first-token time was 4.80 then 3.87 seconds, and synthesis 2.94 then 0.56 seconds. This narrows the remaining bottleneck to the local model path. It does not establish acceptable realtime latency. Those signed-run results are in [installed-app.json](./installed-app.json), including hashes of the tested bundle; an earlier fast fixture must not hide a slow installed route.

A matched-input comparison using the **signed installed worker** measured the pipeline at 1.55–2.17 seconds to its first audio event, including Whisper but with an exact prepared short prompt. LFM reached that event at 1.01–1.28 seconds. Its arithmetic sample returned the incomplete text “2 plus 2 equals,” while the other route answered correctly; the LFM advice sample also ran longer than the short pipeline response. This small comparison supports keeping the pipeline as the default for now, with LFM selectable for experimentation. It does not justify calling either route production-quality full duplex. The shorter benchmark prompt and explicit preparation explain why these component results are not interchangeable with the installed conversation's 3,484–3,695-character prompts. See [voice-engine-comparison.json](./voice-engine-comparison.json).

The **live OpenAI route** now passes fixed-input tests against GPT-Realtime-2.1, using the signed native output helper. Simple arithmetic and the interrupted follow-up reached the first queued audio at 1.407 and 1.404 seconds after the fixture's last voiced sample. A task-status tool request reached first audio at 1.810 seconds, including its spoken preamble; that tool returned fixed empty task data. The counting request took 2.383 seconds and was interrupted by the next input. Playback stopped 726 ms after that clip began, including 300 ms leading silence, with a 1 ms native stop acknowledgment. This is a real hosted response and native output check, not a human microphone or broad agent-execution check. The final fixture run reported $0.04134, following another successful run at $0.04364. See [realtime-live.json](./realtime-live.json).

The live service rejected restored assistant history encoded as `text`; it requires `output_text`. Both history roles now have regression coverage. The final configuration uses high semantic VAD eagerness to reduce long endpoint waits. The same counting sample's observed endpoint fell from 3.121 to 1.939 seconds across two runs; ordinary questions remained below one second in the final run. This small comparison is not a distribution or proof that every natural pause is handled well. The barge-in harness also binds output metrics to the response that produced them, so audio still arriving from an interrupted reply cannot become a negative first-audio time for the new question. ## Library and model research

### Capture, wake word and turn taking

**AVAudioEngine remains the right capture/output boundary.** It is already integrated with macOS permissions and the floating assistant. Moving microphone ownership into a browser or Python audio stack would add another lifecycle and echo-reference boundary. The current changes keep capture and playback in the same native helper and stream PCM to the service. Cloud audio also uses that boundary. Playback timing records the portion actually heard so the hosted conversation can discard unheard output after interruption.

**Silero remains the VAD.** Its maintained implementation supports streaming inference through ONNX, with small audio frames and CPU operation. Jarvis already has the corresponding runtime and a qualified model revision. The important improvement is scheduling it independently of language generation, not changing the name of the VAD library. [Silero project](https://github.com/snakers4/silero-vad).

**Smart Turn remains the semantic endpoint detector.** Its published input is recent 16 kHz audio, bounded to eight seconds. Jarvis asks after a short VAD pause and ignores an answer if speech has resumed. It retains a silence fallback so a model failure cannot hold the microphone indefinitely. Published CPU timings are implementation context; this Mac's measured figures are recorded separately above. [Smart Turn project](https://github.com/pipecat-ai/smart-turn).

**openWakeWord remains the activation model.** The fixed phrase can be detected locally without transcribing the idle room. Model weights have different licensing from the code: the project's pretrained models use CC BY-NC-SA 4.0. That matters before distributing a commercial bundle; it does not justify changing the working personal model during this fix. The optional bare-name mode remains separate because it uses short local transcription. [openWakeWord documentation](https://github.com/dscripka/openWakeWord/blob/main/README.md).

**LiveKit's turn detector and interruption handling are useful comparisons.** Its current stack distinguishes speech activity, turn completion, and interruptions, and provides a path to evaluate more natural conversational behavior. Adopting its entire transport/agent framework would duplicate Jarvis's existing native audio and task service. The best use here is as a benchmark and design reference before considering a targeted adapter. [LiveKit turn detector](https://docs.livekit.io/agents/logic/turns/turn-detector/).

**sherpa-onnx is the strongest alternative runtime to evaluate if packaging or partial ASR becomes the next bottleneck.** It covers offline and streaming speech recognition, speech synthesis, VAD and other audio capabilities across native platforms. Its Mac and Swift examples make it relevant to a future native worker. Adding it now would duplicate existing ONNX and MLX paths without measured benefit. [sherpa-onnx project](https://github.com/k2-fsa/sherpa-onnx).

### Transcription and speech generation

**MLX Audio is already the useful integration layer.** It supports STT, TTS and STS on Apple silicon, including several relevant model families. Keep the pinned bundled runtime and update a specific adapter only when qualification demonstrates a gain. A blanket dependency upgrade can change processor formats, output chunking, licensing obligations and signing behavior simultaneously. [MLX Audio project](https://github.com/Blaizzy/mlx-audio).

**Voxtral Mini 4B Realtime is streaming ASR, not a conversational speech generator.** Mistral publishes a latency/accuracy tradeoff, recommending 480 ms transcription delay, with selectable shorter and longer delays. It could improve partial transcription but does not replace reasoning or TTS. The published vLLM path and larger weights require a separate Mac evaluation; there is no measured reason to replace the installed small Whisper in this change. [Mistral model card](https://huggingface.co/mistralai/Voxtral-Mini-4B-Realtime-2602).

**Pocket TTS deserves the next focused TTS comparison.** Kyutai publishes a 100M-parameter CPU model with streaming output, roughly 200 ms first chunk and roughly 6× real time on an M4 MacBook Air using two CPU cores. Those are vendor measurements on different hardware. Its CPU placement could reduce contention with MLX reasoning. The current model is English-only, uses CC BY 4.0, and access requires accepting its conditions. It does not supply an agent or turn detector. [Pocket TTS model card](https://huggingface.co/kyutai/pocket-tts).

**Qwen3 TTS 0.6B is another targeted candidate.** Its model family supports streaming speech generation and voice conditioning. It is a larger TTS component than Kokoro; compare startup cost, first chunk, steady output speed and the desired British voice before adopting it. A convincing demo of voice quality alone is insufficient for an always-available assistant. [Qwen3 TTS model card](https://huggingface.co/Qwen/Qwen3-TTS-12Hz-0.6B-Base).

### Direct audio conversation

**LFM2.5 Audio is the current practical local option.** Liquid describes a 1.5B model with audio understanding and generation, including interleaved output. The installed MLX conversion passes Jarvis's behavior checks and generates ahead of playback. The app still endpoints a user turn and performs a short transcript for task/memory routing before using its audio conversation path. Calling that adapter fully duplex would overstate it. The original model uses the LFM Open License, not Apache-2.0. [Liquid model card](https://huggingface.co/LiquidAI/LFM2.5-Audio-1.5B), [Liquid audio documentation](https://docs.liquid.ai/lfm/models/audio-models).

**NemotronLabs VoiceChat is the most relevant larger research candidate for the stated ambition.** NVIDIA's August 2026 release combines continuous speech input/output and a separate function channel. Its published latency and tool results come from NVIDIA GPU evaluation. The MLX community conversion provides a stateful streaming interface, 16 kHz input and 22.05 kHz output, but its 4-bit artifact is about 9.17 GB before session overhead. That exceeds Jarvis's current 4.5 GB residency target by itself. A generic “duplex” role cannot load it through LFM's processor. The bundled library contains a model implementation, but Jarvis still needs codec, function-channel, session and memory-budget integration. It remains disabled, not passed or declared incompatible merely because it is large. [NVIDIA model card](https://huggingface.co/nvidia/NVIDIA-NemotronLabs-VoiceChat-11B), [MLX conversion documentation](https://huggingface.co/mlx-community/NemotronLabs-VoiceChat-11B-4bit).

**MiniCPM-o 4.5 has a real Mac path, with a material hardware qualification.** Its authors describe a 9B multimodal model and llama.cpp-omni support for Mac deployment. Their stated requirements are M3/M4/M5 with at least 16 GB for half duplex, and M4 Max with at least 24 GB for full duplex. This M1 Pro/16 GB is below those published configurations. Its research profile stays disabled rather than borrowing LFM's qualification. [MiniCPM-o model card and device requirements](https://huggingface.co/openbmb/MiniCPM-o-4_5).

**PersonaPlex is a useful conversational benchmark, not a proven drop-in Mac backend.** NVIDIA publishes interruption, turn-taking and backchannel results, with an A100 80 GB listed as evaluation hardware. The model has its own Moshi-based runtime and NVIDIA Open Model License. Those results establish why full-duplex modeling is interesting; they do not establish suitable latency, memory use or reliable tool execution in this app. [PersonaPlex model card](https://huggingface.co/nvidia/personaplex-7b-v1).

### OpenAI and agents

**OpenAI Realtime is integrated as a distinct transport.** Current official documentation names GPT-Realtime-2.1, semantic VAD and WebSocket audio events. A socket client must stop local playback and truncate unheard assistant audio when a user interrupts; server-side response cancellation alone does not empty a native output queue. The new adapter handles both. Credentials stay in Keychain and the service process. Local-only mode prohibits the route; choosing it never silently falls back to a paid provider. [WebSocket guide](https://developers.openai.com/api/docs/guides/voice-websockets), [Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations), [VAD guide](https://developers.openai.com/api/docs/guides/realtime-vad).

The published GPT-Realtime-2.1 prices used for reported-usage estimates are $4/$24 per million input/output text tokens and $32/$64 for input/output audio tokens, with $0.40 cached input. Higher reasoning effort can increase latency and token use. Jarvis's response-reported stop is not an account billing guarantee: usage arrives after generation and the separate transcription cost is not included in this estimate. The user connected the provider and approved a $1 test ceiling before live audio was sent. [OpenAI model and pricing details](https://developers.openai.com/api/docs/models/gpt-realtime-2.1).

**Hermes provides the useful learning pattern.** Its documented skills use progressive disclosure: list metadata, load the needed instructions, then load referenced material on demand. It can create and improve skills from experience; its write-approval mode stages changes for review. Jarvis adopts the compatible instruction format and an outcome-linked memory proposal path. It does not claim to include Hermes's complete backend, marketplace, background review or training system. [Hermes skills documentation](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills/), [Agent Skills specification](https://agentskills.io/specification).

**OpenClaw is a capability-management reference.** Its plugin inventory distinguishes executable plugins, compatible bundles and skills; installation does not grant every runtime, OAuth or operating-system permission. Jarvis's current MCP connections and skill packages provide the first practical extension paths while retaining the supplied plan's reviewed-effect contract. An OpenClaw-compatible marketplace importer would be an additional feature, not something implied by copying a SKILL.md. [OpenClaw plugins](https://docs.openclaw.ai/plugins), [OpenClaw installation reference](https://docs.openclaw.ai/cli/plugins/install), [OpenClaw skills](https://docs.openclaw.ai/skills).

## Learning and awareness: implemented meaning

Jarvis can describe its actual engine, selected project, available models, permissions, listening state and observed task results. It can retrieve approved scoped memories and notes, accept corrections, delete derived vectors when forgetting, and propose procedural lessons from completed work. This is operational context and persistent learning through recall. It is not evidence of consciousness, autonomous changes to model weights, or reliable self-modification.

Improvements to Jarvis's code should themselves be ordinary scoped tasks: prepare a worktree, implement, check the exact revision, show the result and retain a rollback path. A model's statement that it improved itself is not evidence. Similarly, a proposed memory should not become a fact merely because the model generated it. The existing review state and provenance fields remain the authority.

## Plan status and remaining release gates

1. **Native experience:** the orb geometry and design are retained. Display permutations, full-screen Spaces, keyboard docking, accessibility preferences and 60 fps remain separate device checks.
2. **Durable core:** revision-bound approvals and effect recovery are retained; receipts now include provider/session identifiers. General agent effects use the same ledger. A model summary is logged separately from verified evidence.
3. **Conversation:** local endpointing, interruption wiring, concise output, streamed wake recognition and actual hosted transport are implemented. Local ASR still finalizes recordings; live human acoustic qualification remains necessary.
4. **Coding workflows:** the existing Codex/Claude adapters are retained, alongside reviewed local commands in isolated worktrees. Real paid implement/review/check cycles require connected credentials. A successful fixture is not a successful external provider run.
5. **Context and memory:** scoped recall, correction, derived deletion and selected context remain intact. General agent lessons use the same review queue. Arbitrary GUI control is not inferred from synthetic grounding results.
6. **Release:** build, signing, installed launch and runtime checks must be read from the current release evidence. Notarization, clean-machine installation and all migration scenarios cannot be marked complete from a developer launch.
7. **Routines:** existing scoped routines/watchpoints remain. Jarvis must be running; sleep/resume re-arms listening. Long-duration routine completion and sustained audio performance under agent load remain qualification work.
8. **Connections:** MCP execution is added. Existing read-only Apple/Google/browser paths are retained. Mail sending, Google writes, arbitrary browser content and coordinate-only vision clicking are not falsely advertised as complete.

For voice acceptance, record first transcript, first model token, first playable audio, endpoint delay and interruption latency separately. Run at least 100 human interruption trials per intended audio route, including pauses, backchannels, fan noise, overlapping playback, Bluetooth changes and sleep/wake. Record failures as well as averages, and compare the same utterances and prompt sizes. The release bar is a reliable observed interaction, not the number of libraries installed.

The companion [STATUS.md](./STATUS.md) and JSON evidence files distinguish code, fixtures, actual native output, application behavior and remaining live checks. All external sources above were accessed on 12 September 2026; publisher benchmark numbers remain attributed to their original hardware and test setup.

## Wake-name repair after microphone feedback

The user reported that neither “Hey Jarvis” nor “Jarvis” worked in normal use. The former installation had bare-name wake disabled, a fixed phrase model, and no proof that frames were reaching the detector. A successful synthesized sample and an open microphone were insufficient acceptance evidence.

The new local adapter uses [Sherpa-ONNX English keyword spotting](https://k2-fsa.github.io/sherpa/onnx/kws/pretrained_models/index.html) with the 3.3M GigaSpeech model. The pinned int8 weights use about 5 MB. SentencePiece encodes a chosen English name without training a new phrase model. The existing openWakeWord route remains available for the default name when the new adapter is unavailable.

Qualification now includes three takes of both full and bare names, a second voice, a custom name, old-name rejection and silence: 19 checks passed. Wider beam decoding recovered misses, but a confusable phrase (“your service”) triggered a bare-name candidate. The application therefore confirms bare candidates with a short, bounded local Whisper transcription. The recorded confusing negative is rejected by that confirmation. This additional work is unnecessary for a recognized full “Hey …” phrase. `keyword.json` records nine streamed cases, including detection while Qwen was generating and no dropped listener frames. These are synthesized input tests, not human acoustic acceptance.

The service now reports detector readiness separately from received frames, records speech activity, recovers a stalled listener, and offers a 15-second microphone wake check. Naming settings are validated, persisted with an explicit Save button, and used in wake recognition, ASR hints, address removal and conversation instructions. A name-only wake acknowledges the user and reopens the microphone. It no longer ends as an empty conversation.

`local-conversation.json` uses the actual service, encrypted store, local models, native playback and scoped file executor with simulated input. It verifies four → double that → eight, approved memory and recall, an exact file effect and its receipt, and full/bare custom-name wake followed by a spoken question. The final warm run measured 0.68–1.68 seconds to playback for its typed cases, and 2.25–3.25 seconds from recording close to playback for the spoken follow-ups. Earlier controlled runs ranged up to 3.4 seconds. These values exclude endpointing delay and do not replace an installed microphone measurement.
